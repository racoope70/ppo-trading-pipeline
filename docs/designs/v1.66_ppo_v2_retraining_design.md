# v1.66 PPO v2 Retraining Design

## Purpose

Design a PPO v2 retraining plan after the legacy PPO was closed as infrastructure fixture only.

The legacy PPO failed trading-edge promotion under the stricter audit framework and remains valid only for infrastructure validation, audit baseline comparison, and future PPO v2 benchmark comparison.

v1.66 defines the design requirements for a future PPO v2 retraining path.

v1.66 is not a retraining-execution milestone.

v1.66 is not a deployment milestone.

v1.66 is not a controlled-submit milestone.

## Starting Point

The sealed starting point is:

```text
v1.65-legacy-ppo-final-audit-decision
latest sealed commit = 23d7736
tests = 227 passed, 2 warnings
```

The v1.65 final decision closed the legacy PPO as:

```text
legacy_ppo_final_classification = INFRASTRUCTURE_FIXTURE_ONLY
trading_edge_decision = FAIL_FOR_TRADING_EDGE
controlled_submit_decision = REJECT_FOR_CONTROLLED_SUBMIT

```

## Why PPO v2 Instead of Legacy PPO Retraining

The legacy PPO should not be retrained directly because the audit path concluded that it failed trading-edge promotion.

The legacy PPO passed infrastructure use but did not pass the stricter standard needed for trading-edge claims.

The legacy PPO remains useful for:

```text
artifact-loading validation
feature-alignment validation
prediction-pipeline validation
broker connectivity validation
NO-SUBMIT safety validation
reporting-chain validation
audit baseline comparison
future PPO v2 benchmark comparison
```

The legacy PPO is not valid for:

```text
controlled paper submit
live trading
hybrid deployment
claiming trading edge
feature-importance based promotion
production readiness
```

PPO v2 should be treated as a new governed candidate with a clean retraining design, not a continuation of the failed legacy model.

## Data Requirements

The planned canonical data source is:

```text
Alpaca historical 1-hour stock bars
```

The planned baseline universe is:

```text
AAPL
AMD
MRK
PFE
UNH
XOM
```

Any universe expansion requires a future checkpoint.

The data design must include:

```text
explicit source documentation
data extraction parameters
timestamp range documentation
symbol-level coverage checks
missing-bar checks
duplicate-bar checks
market-session consistency checks
corporate-action awareness
reproducible dataset generation
clear raw-data and processed-data separation
```

Generated datasets must remain excluded from version control unless a later checkpoint explicitly authorizes a small documented sample or metadata file.

## Split Design

PPO v2 must preserve strict temporal separation:

```text
train_df   = model fitting only
embargo    = temporal gap
eval_df    = walk-forward evaluation
holdout_df = untouched final validation
```

Required split controls:

```text
no temporal overlap
no leakage
embargo between train and eval
holdout isolated from all tuning
holdout used only after model selection
no repeated tuning against holdout
no model promotion without holdout review
```

The holdout set must remain untouched until final validation.

## Walk-Forward Design

PPO v2 must use multiple train/eval windows.

The walk-forward design must document:

```text
window definitions
train period length
embargo length
eval period length
symbol coverage by window
metric definitions
candidate-selection rules
window aggregation rules
```

The walk-forward review must include:

```text
symbol-level metrics
portfolio-level metrics
net-of-cost performance
benchmark-relative performance
drawdown
turnover
trade frequency
stability across windows
```

Promotion must not depend on one favorable window.

## Holdout Design

The holdout set must be reserved before model selection.

The holdout set must not be used for:

```text
hyperparameter search
feature selection
normalization fitting
candidate ranking
threshold tuning
model-selection iteration
manual cherry-picking
```

A PPO v2 model that performs well in walk-forward evaluation but fails holdout review cannot advance beyond offline review.

## Preprocessing and Normalization Controls

All preprocessing must be train-only.

Required controls:

```text
fit scalers only on train_df
fit VecNormalize statistics only on train_df
fit feature transforms only on train_df
apply locked train statistics to eval_df
apply locked train statistics to holdout_df
prevent eval leakage into preprocessing
prevent holdout leakage into preprocessing
```

Evaluation constraints remain:

```text
eval_env.training = False
eval_env.norm_reward = False
```

## Feature Governance

PPO v2 must use the safe feature manifest.

The following fields must not enter model feature inputs:

```text
Target
Return
Datetime
Symbol
```

These fields may be used for:

```text
labeling
evaluation
grouping
auditing
reporting
```

Feature additions require leakage review.

Feature importance is allowed only as interpretability after validation.

Feature importance must not be used as proof of trading edge.

## Cost, Slippage, and Market Friction Assumptions

PPO v2 evaluation must be net of trading frictions.

The design must document:

```text
cost assumptions
slippage assumptions
turnover
trade frequency
friction sensitivity testing
effect of higher cost assumptions
effect of higher slippage assumptions
```

A model whose edge disappears under reasonable friction assumptions must be rejected or redesigned.

## Benchmark Requirements

PPO v2 must be evaluated against:

```text
cash / no-trade baseline
buy-and-hold baseline
equal-weight portfolio baseline where applicable
legacy PPO infrastructure baseline where applicable
```

Promotion cannot rely on:

```text
positive Sharpe alone
cash outperformance alone
one strong window
one strong symbol
feature importance
```

Promotion requires benchmark-relative evidence.

## Model-Selection Rules

Model selection must be predeclared.

Selection should require:

```text
majority-window benchmark support
positive median PPO-vs-buy-and-hold
positive net-of-cost performance
acceptable drawdown
stable risk-adjusted returns
reasonable turnover
reasonable trade frequency
no unexplained single-symbol dependence
holdout confirmation
```

Selection must not be based only on:

```text
best Sharpe
best single window
cash outperformance
one favorable market regime
feature-importance explanation
```

## Risk and Robustness Requirements

PPO v2 review must include:

```text
maximum drawdown review
Sharpe review
Sortino review where available
win-rate review
turnover review
trade-frequency review
per-symbol performance review
portfolio-level performance review
window stability review
regime sensitivity review where available
friction sensitivity review
```

A PPO v2 candidate must be rejected or redesigned if it shows unstable or excessive risk.

## Artifact Governance

PPO v2 must use isolated artifact paths.

Required artifact rules:

```text
do not overwrite legacy PPO artifacts
do not overwrite validated artifacts
document artifact paths before execution
keep generated models out of version control
keep generated datasets out of version control
keep generated reports out of version control unless explicitly documented
keep generated logs out of version control unless explicitly documented
```

Expected future artifact planning should define separate directories for:

```text
raw data
processed data
training reports
walk-forward reports
holdout reports
model artifacts
audit summaries
```

v1.66 does not create these generated artifacts.

## Promotion Gates

PPO v2 must follow the v1.64 promotion framework:

```text
Level 0 = Infrastructure Baseline
Level 1 = Offline Model Quality Candidate
Level 2 = No-Submit Observation Candidate
Level 3 = Controlled-Submit Eligible Candidate
Level 4 = Production / Live Trading Candidate
```

v1.66 does not promote PPO v2 to any level.

v1.66 only defines the design required before a future authorization checkpoint.

## Rejection Criteria

Reject or redesign PPO v2 if:

```text
benchmark evidence is weak
median PPO-vs-buy-and-hold is negative
costs erase the edge
drawdown is excessive
turnover is excessive
trade frequency is excessive
leakage controls are incomplete
holdout is reused for tuning
performance depends on one window
performance depends on one symbol
candidate behavior is unstable
feature importance is used as proof of edge
positive Sharpe is the only support
cash outperformance is the only support
```
