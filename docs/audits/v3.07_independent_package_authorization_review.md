# v3.07 Independent Package Authorization Review

Repository: `racoope70/ppo-trading-pipeline`
Review type: Independent v3.07 package authorization review
Final decision: `FAIL -- do not authorize training`

---

## 1. Final Decision

```text
FAIL -- do not authorize training
```

The new v3.07 package is materially better than the prior failed v3.07 package because it defines an exact command, config, run id, ticker universe, feature set, temporal windows, embargo windows, seed policy, quarantine/log paths, and post-run audit boundary.

However, it is not sufficient to authorize one-time no-submit PPO v2 training because the reviewed command still points to a non-executing scaffold, the sealed CLI arguments are not implemented by that module, preflight has not passed, and the package repeatedly classifies itself as static package preparation only rather than execution-ready.

## 3. What Passed

The package defines an exact intended command with `--no-submit`, run id, config path, quarantine root, log root, stdout/stderr paths, artifact inventory path, and checksum manifest path.

The config defines a specific run id, package root, local input dataset path, quarantine/log paths, six-ticker universe, data source, temporal split windows, embargo windows, feature set, seed policy, and PPO training parameters.

The ticker, feature, temporal split, data-source, and seed manifests are no longer placeholders at the package-documentation level. They define AAPL, AMD, MRK, PFE, UNH, XOM; the intended feature columns; train/eval/holdout windows; Alpaca historical 1-hour bars as the intended source; and fixed seeds of 70.

The package defines future preflight gates for data contract validation, missing-bar coverage, split boundaries, embargo, holdout usage, handoff validation, leakage rejection, runtime snapshot, no-submit enforcement, broker/order/promotion/hybrid-disabled checks, source-code dependency review, and command-argument compatibility review.

Generated PPO v2 quarantine/log outputs are protected by `.gitignore`, including `artifacts/ppo_v2/quarantine/*` and `artifacts/ppo_v2/logs/*`, while allowing optional `.gitkeep` placeholders.

The package preserves no-submit and blocks paper orders, live orders, controlled submit, model promotion, PPO + RF, PPO + XGBoost, trading-edge claims, and profitability claims.

The v3.08 post-run audit requirement is clear: metrics, reports, promotion, deployment, paper/live orders, controlled submit, PPO + RF, PPO + XGBoost, and trading-edge/profitability claims remain blocked before v3.08.

## 4. Blocking Findings

### B1 -- The Command Still Points to a Non-Executing Scaffold

The command targets:

```text
../.venv/bin/python -m src.ppo_v2_controlled_training_execution ...
```

But `src/ppo_v2_controlled_training_execution.py` explicitly states that it is a non-executing controlled execution scaffold and that it does not train a model, fetch data, write datasets, create model artifacts, promote models, or submit orders.

The module's manifest construction also hard-codes `training_authorized = False`, `training_execution_authorized = False`, `artifact_creation_authorized = False`, `data_fetching_authorized = False`, `dataset_write_authorized = False`, and all order/hybrid flags as false.

This blocks authorization.

### B2 -- The Sealed Command Arguments Are Not Implemented by the Target Module

The packaged command includes CLI flags such as:

```text
--mode
--run-id
--config
--quarantine-root
--log-root
--stdout-path
--stderr-path
--artifact-inventory-path
--checksum-manifest-path
--no-submit
```

The target module does not define a CLI parser, `main()`, or `if __name__ == "__main__"` entrypoint in the reviewed source. Its exported API is only dataclasses and `build_ppo_v2_controlled_training_execution`.

By contrast, the actual training module `src/train.py` has a CLI entrypoint and calls `model.learn(...)`, but that is not the command selected by the v3.07 package.

This blocks authorization.

### B3 -- Preflight Requirements Are Future-Only and Have Not Passed

The preflight manifest states:

```text
execution_authorized = false
training_execution_authorized = false
preflight_executed = false
execution_ready_proven = false
source_code_execution_dependency_resolved = false
```

It defines what future preflight must check, but it does not provide passing preflight evidence.

This blocks authorization.

### B4 -- The Package Itself Says B3 and B5 Are Not Fully Resolved

The package-preparation run record states:

```text
B3 is addressed only at the package-documentation boundary, not at the executable source-code boundary.
B5 is addressed only by defining future preflight requirements, not by proving execution readiness.
```

The non-authorization manifest repeats that the package does not prove the command can train and does not resolve the source-code execution dependency.

This blocks authorization.

### B5 -- The Package Classifies Itself as Static Preparation Only / Do-Not-Run

The command file says:

```text
classification = STATIC_PACKAGE_PREPARATION_ONLY
execution_authorized = false
training_authorized = false
do_not_run = true
```

The README likewise states the package is static-only, does not authorize v3.07 execution, does not authorize PPO v2 training, does not prove the command can train, does not prove execution readiness, and does not resolve the source-code execution dependency.

This blocks authorization.

### B6 -- The Sealed Local Input Dataset Is Referenced but Not Proven Available or Validated

The config points to:

```text
data/processed/ppo_v2/v3_07_no_submit_training_input.parquet
```

and the data-source manifest says the package uses pre-existing local input only, with no data fetching or dataset generation authorized.

But the manifest only says future authorization review must confirm the dataset exists and passes provenance/schema/coverage checks.

This blocks authorization because a PASS must not authorize data fetching or unreviewed dataset generation, and the package has not supplied passing validation evidence for the sealed local input.

## 6. Required Next Action

Before another v3.07 authorization review, the repo needs all of the following:

1. A reviewed source-code implementation checkpoint that makes the selected command entrypoint actually perform the intended one-time PPO v2 no-submit training, or a revised command pointing to a reviewed executable training entrypoint.
2. Proof that the exact sealed command arguments are accepted by the command entrypoint.
3. Passing preflight evidence recorded before execution, including data-contract validation, missing-bar coverage, split/embargo validation, handoff validation, no-submit enforcement, and broker/order/promotion/hybrid-disabled checks.
4. Evidence that the sealed local input dataset exists, matches the reviewed data-source/ticker/feature/temporal assumptions, and was not created by an unreviewed data-fetching or dataset-generation step.
5. Runtime/dependency snapshot and clean/dirty git-state evidence.
6. Updated package status showing execution readiness without contradicting `PROJECT_CONTEXT.md`, while preserving no-submit, quarantine-only outputs, no paper/live orders, no controlled submit, no promotion, no PPO + RF, no PPO + XGBoost, and v3.08 post-run audit requirement.

Final decision: `FAIL -- do not authorize training`.
