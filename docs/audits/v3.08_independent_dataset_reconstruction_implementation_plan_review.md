It uses generic manifest field names such as `source_client` and `retrieval_method` without assigning their required values.

This is a remediable contract-completeness omission.

The plan states that before implementation authorization can be reconsidered, a separate runtime-verification checkpoint must confirm the installed version, XNYS availability, schedule coverage, UTC opens and closes, holidays, early closes, whole-interval slot counts, determinism, and transitive dependency versions.

The governing final contract states the same requirement:

```text
Deferred calendar runtime verification is not acceptable for implementation authorization.
Before implementation authorization can be reconsidered, the separately authorized runtime verification must be completed.
```

However, the plan's numbered sequence places the checkpoints in this order:

1. Independent plan review.
2. Implementation authorization.
3. Dependency/requirements authorization.
4. Dependency installation and runtime verification.
5. Source/test implementation.

`PROJECT_CONTEXT.md` and the milestone map repeat this same order.

These statements cannot all be true simultaneously. Runtime verification cannot be a prerequisite to implementation authorization while also being scheduled after that authorization.


## 11. Risks or inconsistencies found

### Blocking finding 1 — Gate-order contradiction

The plan and final contract state that XNYS runtime verification is required before implementation authorization can be reconsidered, while the future sequence places implementation authorization before runtime verification.

### Blocking finding 2 — Unsafe future freshness anchor

The plan's future execution-head guardrail uses:

```text
git merge-base --is-ancestor 20b454762afa11255aa6e225ae3d781151bb53ea HEAD
```

and declares that planning-authorization commit the active required anchor.

That commit predates:

- creation of the implementation plan;
- cleanup commit `f0063e1c815ddb729c9330f7325592a79ec42dae`;
- current source-of-truth alignment commit `12082e5b40322918c39288397da8c19128314358`;
- this independent review; and
- any future implementation-authorization record.

A checkout containing `20b454762afa11255aa6e225ae3d781151bb53ea` but omitting the cleaned plan and later governance decisions could satisfy this guardrail. It is therefore not safe for future execution.

### Blocking finding 3 — Unmarked stale implementation-plan review

`docs/runs/v3.08_dataset_reconstruction_implementation_plan_review.md` retains active-looking v3.07 target framing, recovered-contract language, an old PASS decision, and obsolete commit anchors without an explicit superseded or historical-only marker.

### Remediable finding 4 — Client/method literals not explicit in the plan

The plan should explicitly bind:

```text
StockHistoricalDataClient
StockHistoricalDataClient.get_stock_bars
```

rather than relying on generic manifest field names and inference from the final contract.

### Non-blocking limitation — CI verification

`Tests #411 passed` is recorded by the repository source-of-truth files, but no corresponding status or workflow run was independently returned by the available GitHub interfaces.

1. Resolve the gate-order contradiction.

   Align the implementation plan, `PROJECT_CONTEXT.md`, and the milestone map with the final contract.

   Unless the final contract is formally amended through a separately reviewed contract-resolution checkpoint, the sequence must be:

   ```text
   independent implementation-plan review
   dependency/requirements authorization
   dependency installation
   XNYS runtime verification
   implementation authorization
   source/test implementation
   mocked unit/contract testing
   data-fetch authorization
   dataset-generation authorization
   dataset evidence review
   dataset-validation authorization
   preflight authorization
   training authorization
   ```

2. Replace the obsolete execution freshness anchor.

   Remove `20b454762afa11255aa6e225ae3d781151bb53ea` as the future implementation/runtime execution anchor.

   The eventual execution guardrail must require ancestry from the later, exact implementation-authorization commit—or another explicitly governed post-review authorization anchor—and must include the cleaned plan, repeated independent review, and final authorization record.

3. Disambiguate the stale implementation-plan-review record.

   Mark `docs/runs/v3.08_dataset_reconstruction_implementation_plan_review.md` clearly as superseded and historical-only, or relocate it to an archive while preserving its historical contents.

   Its v3.07 target, recovered-contract terminology, old PASS decision, and old commit anchors must not remain capable of being interpreted as current governance.

4. Add explicit Alpaca client and retrieval-method literals to the plan.

   The proposed source and mocked-test sections must explicitly require:

   ```text
   source_client = StockHistoricalDataClient
   request_class = StockBarsRequest
   retrieval_method = StockHistoricalDataClient.get_stock_bars
   ```

5. Repeat this independent implementation-plan review after remediation.

   Implementation authorization must remain blocked until the repeated review passes.
