# 2. Summary judgment

The project should proceed at the **contract-governance level** with a:

```text
superseding governed Alpaca-aligned reconstruction
```

It should not proceed as:

```text
byte-identical original dataset recovery
```

The original dataset has not been recovered, and the feed, adjustment, calendar, timestamp-edge, warm-up, gap, dtype, and serialization choices were not historically proven. The proposed choices are nevertheless reasonable as a new, explicitly approved reconstruction standard.

The best posture is:

```text
historical_identity = NOT_PROVEN
reconstruction_type = SUPERSEDING_GOVERNED_ALPACA_ALIGNED_RECONSTRUCTION
operational_execution = BLOCKED_PENDING_FINAL_CONTRACT_RECORD_AND_REVIEW
```

A later recovery of the original artifact could support a separate comparison or lineage review, but it must not retroactively convert the superseding reconstruction into a byte-identical recovery claim.

The repository itself says the controlled deferrals must be resolved before implementation authorization and preserves every execution restriction.

The active repository already contains the proposed Alpaca interface and an IEX default, but that default is implementation evidence, not proof of historical provenance.    The validation repository separately uses an explicit `iex`/`1H` paper-trading configuration, which supports continuity but does not govern the active repository.

Alpaca-py exposes `RAW`, `SPLIT`, `DIVIDEND`, and `ALL`, and `StockBarsRequest.adjustment` is optional. The optional field must not be treated as a historical policy decision.

The SDK directly describes `Bar.timestamp` as the opening timestamp.  The uploaded external report further supports left-edge semantics while warning that a built-in 09:30-aligned hourly regime is not documented. 

The repository supports the 50-bar warm-up minimum and no-synthetic-bars direction, but it leaves the exact retrieval start, session rule, and row-count methodology for later resolution.

# 4. Recommended final decision package

## Choice 1 — Source interface

```text
source_mode = API_HISTORICAL_BARS
client_interface = alpaca.data.historical.StockHistoricalDataClient
request_interface = alpaca.data.requests.StockBarsRequest
retrieval_method = StockHistoricalDataClient.get_stock_bars
alpaca_py_version = EXACT_PIN_REQUIRED
implicit_or_alternative_interface = PROHIBITED
```

The exact `alpaca-py` version must appear as a literal in the contract-resolution record.

## Choice 2 — Feed

```text
feed = DataFeed.IEX
feed_omission = PROHIBITED
feed_auto_resolution = PROHIBITED
feed_classification = DEPLOYMENT_ALIGNED_POLICY
historical_feed_identity = NOT_PROVEN
```

IEX is the best choice under the stated priority of active-loader and paper-trading continuity. It must not be described as proven original-dataset provenance.

## Choice 3 — Adjustment

```text
adjustment = Adjustment.RAW
adjustment_omission = PROHIBITED
rest_only_spin_off_or_combination_modes = NOT_SELECTED
historical_adjustment_identity = NOT_PROVEN
```

RAW is preferable to omission because it prevents provider-default or SDK-version behavior from silently governing the dataset.

## Choice 4 — Warm-up

Use separate rules for calculating the request start and validating actual sufficiency:

```text
retrieval_start_counting_basis =
    expected eligible bar slots under the approved calendar and interval contract

warmup_sufficiency_basis =
    observed valid bars for each symbol after normalization, deduplication,
    session filtering, and validity checks

minimum_observed_warmup_bars_per_symbol = 50
warmup_bars_must_be_strictly_before_contract_start = TRUE
adaptive_per_symbol_retrieval_start = PROHIBITED
insufficient_symbol_warmup = FAIL_CLOSED
exact_raw_retrieval_start = REQUIRED_LITERAL
```

This avoids using an unknown observed dataset to define the request start. The exact UTC timestamp remains a blocker until calculated from the final choices 5–7 and recorded.

## Choice 5 — Calendar

```text
calendar_library = exchange_calendars
calendar_identifier = XNYS
calendar_version = EXACT_PIN_REQUIRED
calendar_role = CANONICAL_SESSION_CALENDAR_FOR_ALL_SIX_SYMBOLS
early_closes = USE_PINNED_XNYS_SCHEDULE
holidays = USE_PINNED_XNYS_SCHEDULE
NYSE_and_Alpaca_calendars = VERIFICATION_REFERENCES_ONLY
runtime_live_calendar_lookup = NOT_GOVERNING
```

The record must acknowledge that XNYS is a selected canonical US-equity calendar, not recovered proof of the original per-symbol calendar.

## Choice 6 — Timezone and filtering order

```text
1. Reject missing or timezone-naive provider timestamps.
2. Interpret provider timestamps as timezone-aware UTC.
3. Apply the approved bar-open and interval-duration semantics.
4. Obtain the applicable XNYS session open and close in UTC.
5. Apply the approved whole-interval session eligibility rule.
6. Preserve the provider bar-open timestamp; do not relabel it as a close.
7. Sort and serialize Datetime as timezone-aware UTC.
```

Calendar-local time may be used internally for human-readable evidence, but the governing comparison should use timezone-aware instants rather than manual clock-string filtering.

## Choice 7 — Bar semantics

My recommended superseding choice is:

```text
bar_source_timeframe = Alpaca TimeFrame.Hour
bar_timestamp = OPEN_TIMESTAMP
bar_interval = [timestamp, timestamp + 1 hour)
interval_edge = LEFT_CLOSED_RIGHT_OPEN
provider_bar_relabeling = PROHIBITED
custom_09_30_reaggregation = NOT_SELECTED
regular_session_eligibility =
    retain only provider intervals fully contained within the approved XNYS session
partial_session_edge_bars = EXCLUDED
```

This is the cleanest provider-aligned rule because it does not contaminate regular-session data with intervals extending outside the session.

The contract must explicitly state the consequence:

```text
contract_start is a temporal eligibility boundary.
It is not a guarantee that the first retained provider bar has Datetime exactly
equal to contract_start.
```

If managerial governance instead requires complete 09:30–16:00 coverage, then this choice must be rejected and replaced by a separately approved minute-bar/custom-aggregation contract. That would be a materially different source and construction policy.

## Choice 8 — Missing bars

```text
synthetic_bars = PROHIBITED
forward_fill_OHLCV = PROHIBITED
backfill_OHLCV = PROHIBITED
duplicate_symbol_datetime = REJECT
expected_bar_slots =
    derived from the pinned XNYS calendar and approved provider-hour interval rule

holiday_or_early_close_non_slots = NOT_GAPS
missing_expected_slot = REPORT_WITH_SYMBOL_AND_TIMESTAMP
any_contract_window_missing_expected_slot = FAIL_CLOSED
warmup_missingness_causing_fewer_than_50_valid_bars = FAIL_CLOSED
cross_symbol_row_count_mismatch = REPORT_AND_FAIL_UNLESS_EXPLAINED_BY_APPROVED_CALENDAR_RULE
```

This is stricter and more auditable than the phrase “gaps that violate required coverage,” which is currently circular.

## Choice 9 — Parquet, dtype, and serialization

Repository runtime evidence already recorded `pandas 3.0.2` and `pyarrow 24.0.0`; those versions are defensible candidates for the superseding profile, although their selection still requires approval.

Recommended baseline:

```text
pandas_version = 3.0.2
pyarrow_version = 24.0.0
parquet_engine = pyarrow

column_order =
    Symbol,
    Datetime,
    Open,
    High,
    Low,
    Close,
    Volume,
    then remaining configured feature columns in manifest order

sort_order = Symbol ASC, Datetime ASC
index = FALSE

Symbol = Arrow utf8 string, non-null
Datetime = timestamp[ns, tz=UTC], non-null
all model feature columns = float64, non-null and finite

object_dtype = PROHIBITED
positive_infinity = PROHIBITED
negative_infinity = PROHIBITED
NaN_in_final_output = PROHIBITED
null_in_required_columns = PROHIBITED
```

The following writer settings must also be literal rather than omitted:

```text
parquet_format_version
compression
data_page_version
dictionary_encoding_policy
statistics_policy
store_schema
row_group_size
timestamp_coercion_policy
allow_truncated_timestamps
```

A defensible starting profile would explicitly freeze the PyArrow 24 documented defaults rather than rely on them implicitly:

```text
parquet_format_version = 2.6
compression = snappy
data_page_version = 1.0
use_dictionary = TRUE
write_statistics = TRUE
store_schema = TRUE
```

However, the exact `row_group_size` and timestamp-coercion values still require a literal managerial selection before authorization. The repository currently requires the full serialization contract but has not bound those values.

# 6. Remaining blockers before code implementation authorization

The following must be completed before a superseding authorization can pass:

1. Record the exact `alpaca-py` version and complete source-interface parameters.
2. Record `IEX` and `RAW` as explicit approved policies, including the non-historical classification.
3. Select and record the exact `exchange_calendars` version.
4. Calculate and record one exact UTC raw retrieval start.
5. Formally approve the distinction between:

   * provider-defined 1-hour bars, and
   * custom 09:30-aligned aggregation.
6. Record the exact interval containment/edge-bar rule and its expected full-day and early-close row-count consequences.
7. Define the expected-slot methodology and fail-closed missing-bar thresholds.
8. Record the complete Arrow schema, including every column and nullability rule.
9. Record every Parquet writer literal, including fixed row-group and timestamp-coercion settings.
10. Resolve whether the stated `contract_start = 2023-01-03T14:30:00Z` is only an eligibility boundary or is expected to equal an actual first retained timestamp.
11. Create the formal contract-resolution record with explicit user/governance approval.
12. Commit that record and obtain green CI.
13. Perform an independent review of the committed contract-resolution record.
14. Confirm execution-head freshness against that reviewed commit.
15. Only then request a separate superseding code implementation authorization.

None of those actions should be interpreted as authorization to fetch or construct the dataset.
