## 6. Findings

### F-01 — SDK automatic retries are not disabled by the draft

```text
finding_id = F-01
severity = MATERIAL_CORRECTABLE
category = AUTOMATIC_RETRY_CONTROL
```

The installed `alpaca-py 0.43.4` source initializes `RESTClient._retry` from `DEFAULT_RETRY_ATTEMPTS`, whose installed value is `3`. Its `_request` loop automatically retries status codes in `DEFAULT_RETRY_EXCEPTION_CODES`, installed as `[429, 504]`. `StockHistoricalDataClient.__init__` does not expose the base client's `retry_attempts` argument. Therefore `automatic_retry_count = 0` and calling `get_stock_bars` only once do not establish that only one provider request will occur.

The draft says retries are prohibited and makes retry need a terminal stop, but it does not require a pre-client, fail-closed verification and disabling mechanism. This fails the audit's explicit PASS criterion. Correct the authorization to require, before client creation, verification that the exact installed SDK/transport retry paths are disabled for the future process, with execution stopping before client creation if zero retries cannot be demonstrably enforced without source or dependency changes. The corrected method must also avoid printing or retaining inspected credential values or prohibited transport data.

### F-02 — the frozen SDK method contains internal pagination capable of a second provider request

```text
finding_id = F-02
severity = MATERIAL_CORRECTABLE
category = REQUEST_COUNT_AND_PAGINATION_CONTROL
```

The installed `StockHistoricalDataClient.get_stock_bars` calls `_get_marketdata`, which loops on `next_page_token`. With `limit = 1`, a normal one-row first response ends before another request because the total-item limit is reached. But an empty response carrying a continuation token, or other unexpected response shape within that loop, can cause another provider request before the caller receives control. Thus the draft's `pagination_authorized = NO`, `request_count_maximum = 1`, and post-response stop conditions do not by themselves enforce a maximum of one transport request.

Correct the authorization to require a verified pre-client mechanism that makes internal pagination incapable of a second HTTP request, and to stop before client creation if that property cannot be established for the exact installed method without a prohibited source/dependency change. A post hoc request counter is not sufficient; the second request must be prevented.

### F-03 — safe exception handling and authentication classification need an explicit deterministic contract

```text
finding_id = F-03
severity = CORRECTABLE
category = EVIDENCE_HANDLING_AND_RESULT_CLASSIFICATION
```

The draft prohibits response bodies, headers, secrets, and raw error content and permits only a sanitized exception class or safely exposed HTTP status. Those output boundaries are appropriate, but the runtime method does not explicitly require catching provider/transport exceptions without rendering the exception message or traceback. The installed SDK constructs `APIError` from response text, so uncaught or stringified exceptions could expose prohibited response content. Correct the draft to require non-rendering exception handling: inspect only the exception type and a safely isolated numeric status when available, never call `str`, `repr`, traceback rendering, or logging on the exception/response/request, and discard exception objects immediately after classification.

The classifications also leave a narrow overlap: an authentication denial caused by invalid credentials could reasonably map to either `BLOCK_...CREDENTIALS_UNAVAILABLE_OR_AMBIGUOUS` or `BLOCK_...AUTHORIZATION_OR_SUBSCRIPTION_DENIED`; the credential label does not say invalid, while the permission label says authorization. Add a deterministic mapping for invalid/unusable credential authentication versus otherwise validly authenticated authorization/entitlement/subscription denial. No diagnostic retry may be used to resolve the distinction.
