## Source Data Contract

The future PPO v2 retraining path may use historical market bars only after a later checkpoint authorizes implementation.

The expected source contract is:

```txt
source = Alpaca historical bars or equivalent validated historical OHLCV source
bar_timeframe = 1 hour
symbols = AAPL, AMD, MRK, PFE, UNH, XOM
timezone = exchange/session-consistent timestamp handling
rows = one row per symbol per bar timestamp
sort_order = symbol ascending, timestamp ascending
duplicate_policy = no duplicate symbol-timestamp rows
missing_bar_policy = explicit validation required before training
```

v1.72 defines the contract only.

v1.72 does not fetch or create this data.

## Feature Contract

Future engineered features must be derived only from information available at or before the decision timestamp.

Allowed feature categories may include:

```txt
lagged returns
rolling volatility
rolling moving averages
rolling price distance measures
rolling volume features
technical indicators using trailing windows only
market-regime labels derived from trailing information only
```

Forbidden feature sources include:

```txt
future returns
forward-filled future targets
same-bar future close information when the decision uses earlier bar information
post-outcome labels
holdout-derived parameters
evaluation-derived parameters
test-derived scaling
leaked symbol-level aggregates computed across future periods
```

`Datetime` and `Symbol` may be retained for indexing, auditability, logging, grouping, and split validation.

## Split Specification

The future PPO v2 retraining process must use time-ordered splits.

Random shuffling is not allowed for time-series training, evaluation, or holdout construction.

The required split structure is:

```txt
train_df = model fitting and train-only preprocessing fit
embargo = unused gap between train and evaluation
eval_df = validation and model-selection evaluation
holdout_df = final untouched out-of-sample validation only
```

## Embargo Specification

An embargo gap must exist between the training window and evaluation window.

The embargo exists to reduce leakage from overlapping rolling features, adjacent labels, and short-horizon autocorrelation.

Minimum embargo rule:

```txt
embargo_window >= max(feature_lookback_window, target_horizon, execution_delay_window)
```

If the future implementation cannot determine the maximum feature lookback, target horizon, and execution delay, it must fail closed.

## Holdout Policy

The holdout set must remain untouched until final validation.

The holdout set must not be used for:

```txt
feature selection
hyperparameter tuning
reward tuning
threshold tuning
model selection
early stopping
normalization fitting
regime fitting
scaler fitting
report tuning
manual iteration
```

The holdout set may be used only for final validation after a candidate model has already been selected using the training and evaluation process.

## Preprocessing Boundary

All preprocessing parameters must be fit on the training split only.

This includes:

```txt
scalers
normalizers
imputers
winsorization thresholds
PCA transformations
regime models
feature bucket boundaries
volatility thresholds
```

The fitted preprocessing objects may then transform evaluation and holdout data.

Evaluation and holdout data must not influence preprocessing fit parameters.

## Leakage Controls

Future implementation must reject any data pipeline that violates:

```txt
future information leakage
cross-split leakage
holdout leakage
symbol leakage through future aggregates
target leakage
normalization leakage
feature engineering leakage
duplicate timestamp leakage
```
