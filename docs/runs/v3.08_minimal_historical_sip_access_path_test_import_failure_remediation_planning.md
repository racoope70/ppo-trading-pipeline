## 10. Risks and fail-closed conditions

The principal risks are repeating the prohibited traceback rendering, converting an evidence-planning task into unauthorized runtime diagnosis, prematurely asserting a corrected import, allowing local inspection to resolve credentials or construct a client, and treating the historical zero-request count as permission for a new request.

Any future checkpoint must fail closed if:

- its authorization, independent review, commit, push, or green-CI condition is incomplete;
- repository freshness or evidence-chain identity is not exact;
- `alpaca-py` is not exactly version `0.43.4`;
- dependency installation, package modification, or repository modification would be required;
- an exception message, representation, or traceback would be rendered or retained;
- sanitized categorical evidence is insufficient to establish the local import surface;
- credential resolution, client creation, network access, provider transport, market-data access, or data work would occur during local diagnosis;
- a second diagnostic file or any script, dump, screenshot, dataset, or artifact would be required;
- the correct import surface remains unknown or disputed after review;
- the corrected authorization does not independently re-establish all retry, pagination, transport-guard, exception-safety, credential, and one-request controls; or
- any rerun, remediation execution, or scope expansion is inferred from this planning draft or from the failed execution's zero invocation counts.

Encountering a stop condition grants no authority to resolve it.
