# Final External-Evidence Decision Recommendation for the Governed PPO v2 Dataset Reconstruction Contract

Historical evidence source: **Deep Research external verification**.

## Executive conclusion

Based on the official Alpaca, pandas, PyArrow, `pandas_market_calendars`, and `exchange_calendars` documentation, plus the public evidence visible in `racoope70/quant-trading-model-validation`, the externally supportable path is **not** a claim of byte-identical recovery of the missing original dataset. The supported path is a **superseding governed Alpaca-aligned reconstruction contract** that makes the ambiguous choices explicit, because Alpaca’s feed choice, adjustment choice, bar aggregation semantics, calendar source, and Parquet writer defaults can all change the resulting dataset materially. Alpaca’s own documentation shows that IEX and SIP can produce different OHLCV bars, that omitted `feed` resolves to the “best” feed available under an account’s subscription, that omitted bar `adjustment` defaults to `raw`, and that the API may return fewer rows than a requested `limit`, so leaving these surfaces implicit is not contract-safe. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

The public validation repository is useful, but only as **secondary project evidence**. The reviewed public pages show Alpaca usage, a `1H` model timeframe, and an explicit `iex` data feed in the Phase 1 reliability run. It does **not** publicly document an adjustment policy, a historical split/dividend handling policy, a market-calendar implementation, or a Parquet writer contract. That means it helps anchor an Alpaca/IEX/1H managerial decision, but it does not prove the historical properties of the missing original dataset. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

Accordingly, the recommended disposition is to bind all nine choices explicitly as a forward governance policy, label them as **reconstruction-contract decisions rather than recovered historical facts**, and frame the next repo record as a **superseding governed Alpaca-aligned reconstruction contract**. [^DR-ALPACA]

## Official documentation findings

For Alpaca stock bars, the Python SDK’s `StockBarsRequest` exposes `feed` and `adjustment` as optional parameters, treats timezone-naive `start` and `end` datetimes as UTC, and sorts results by timestamp in ascending order by default. The SDK documents `DataFeed.IEX`, `DataFeed.SIP`, and `DataFeed.DELAYED_SIP`, and documents `Adjustment.RAW`, `SPLIT`, `DIVIDEND`, and `ALL`. [^DR-ALPACA][^DR-CALENDAR]

The REST historical stock-bars reference says `start` and `end` are **inclusive**, `limit` defaults to 1000 and may return fewer points than requested, and `adjustment` defaults to `raw`. The REST docs also now document `raw`, `split`, `dividend`, `spin-off`, and `all`, plus comma-separated combinations such as `split,spin-off`. That means the REST surface is broader than the Python SDK enum surface, so a contract written around **alpaca-py** should bind to the SDK’s documented enum values unless governance explicitly chooses to depend on lower-level REST parameter strings instead. [^DR-ALPACA]

Alpaca’s Market Data FAQ states that SIP is the consolidated feed across U.S. exchanges, while IEX is a single exchange. Alpaca also shows an example where the same AAPL daily bar differs between SIP and IEX in prices, trade count, and volume, and states that the default `feed` is the “best” available feed for the user’s subscription. For historical queries, SIP can be queried without a subscription only when the `end` parameter is at least 15 minutes old; recent SIP access and latest endpoints require the relevant subscription. [^DR-ALPACA]

For bar semantics, Alpaca states that minute bars are built from trade timestamps truncated to the minute, that the bar timestamp is the **left side of the interval**, and that bars with no qualifying trades are not emitted. It also states that “all the other non-minute and non-daily bars” are aggregated from minute and daily bars rather than directly from trades. That supports a left-edge interpretation for hourly bars as the Alpaca-aligned choice, but Alpaca does **not** separately publish a dedicated one-hour timestamp statement as explicit as it does for minute bars, so the 1H interpretation is partly an evidence-based inference and not a separately verified historical fact. [^DR-ALPACA]

For calendars, Alpaca’s Trading Calendar endpoint returns market days from 1970 to 2029 and includes specific open and close times, including early closes. `pandas_market_calendars` says its calendars are shipped as package code, not fetched live, that since v2.0 it mirrors calendars from `exchange_calendars`, that since v4.0 it supports interruptions, and that since v5.0 it uses `zoneinfo` instead of `pytz`. `exchange_calendars` exposes `XNYS` directly and provides schedule and session/minute-oriented methods. `pandas_market_calendars` also shows NYSE examples in UTC and a `date_range(..., frequency='1H')` output aligned to **session-relative** times such as `14:30:00+00:00`, `15:30:00+00:00`, and session close, which is useful for schedules but does **not** match Alpaca’s documented left-edge minute-bar convention. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION]

For Parquet, pandas documents that `DataFrame.to_parquet` defaults to `engine='auto'`, `compression='snappy'`, and `index=None`, where `auto` tries `pyarrow` and only falls back to `fastparquet` if needed. PyArrow documents that `write_table` defaults include `version='2.6'`, `compression='snappy'`, `use_dictionary=True`, `write_statistics=True`, `data_page_version='1.0'`, `coerce_timestamps=None`, and `allow_truncated_timestamps=False`. It also documents that Parquet `version='1.0'` maximizes compatibility, while nanosecond timestamps require `version='2.6'`. Arrow’s pandas integration shows that timezone-aware UTC timestamps are preserved into Arrow timestamp types with `tz=UTC`. Pandas further documents that text should use `StringDtype` rather than `object`, and that explicitly nullable integers should use `Int64` rather than relying on inference. [^DR-CALENDAR][^DR-SERIALIZATION]

## Validation repository evidence

The public README for `racoope70/quant-trading-model-validation` describes the repository as the validated research layer between exploratory work and production deployment, says it exports trading signals, and says the dry run “fetches Alpaca bars.” That is strong public evidence that Alpaca is part of the validation/evaluation stack, but it does not by itself establish the historical contract of the missing dataset in the other repository. [^DR-ALPACA][^DR-VALIDATION]

The strongest specific public evidence is the `validation/paper_trading/phase_1_reliability/README.md` page. It states that the reliability run used `Data feed iex`, `Model timeframe 1H`, and Alpaca paper trading. It also says that no missing-bar or stale-prediction failures were observed in that operational run. This is useful secondary evidence in favor of an Alpaca/IEX/1H framing, but it is operational validation evidence, not a historical provenance proof for the original missing dataset. [^DR-ALPACA][^DR-VALIDATION]

On serialization, the public validation folder lists `run_summary_sample.csv`, `symbol_order_fill_summary.csv`, and `artifact_symbol_summary.csv`, and no public README-page mention of Parquet was found in the reviewed pages. That supports the narrower conclusion that the validation repo publicly shows CSV evidence artifacts, not a governing Parquet contract. [^DR-SERIALIZATION][^DR-VALIDATION]

On adjustment policy, market-calendar logic, split handling, yfinance usage, or a non-Alpaca historical source, No explicit public README-page evidence was found in the reviewed pages. That absence matters: it means the validation repo can support an Alpaca-aligned governance decision, but it does not relieve governance from explicitly choosing feed, adjustment, calendar, timestamp semantics, or serialization settings. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

## Recommended bindings

1. **Feed and source interface.**  
   **Verified facts:** Alpaca-py exposes `DataFeed.IEX`, `SIP`, and `DELAYED_SIP`; Alpaca says IEX and SIP can produce materially different bars; and if `feed` is omitted Alpaca uses the “best” available feed based on the account’s subscription. **Validation-repo evidence:** the public Phase 1 reliability page explicitly says `Data feed iex` and `Model timeframe 1H`. **Recommended binding:** bind the contract to **Alpaca historical stock bars via explicit `DataFeed.IEX`**, never to an omitted/default feed. **Why:** this is the only explicit source choice visible in the validation repo, and it removes subscription-dependent ambiguity. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Medium**, because the original missing dataset may have used SIP or an omitted default. **Approval required:** **YES**, because this is a governance choice, not a proven historical fact. [^DR-ALPACA][^DR-VALIDATION]

2. **Adjustment policy.**  
   **Verified facts:** alpaca-py documents `RAW`, `SPLIT`, `DIVIDEND`, and `ALL`; the REST stock-bars reference defaults `adjustment` to `raw` and also documents `spin-off` and combined adjustments at the raw API level. **Validation-repo evidence:** No reviewed public page names an adjustment policy. **Recommended binding:** bind the Alpaca-aligned contract to **explicit `Adjustment.RAW`**. **Why:** `raw` is the documented API default, it is supported directly in alpaca-py, and it is the lowest-assumption choice when the historical policy is unproven. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Medium-low**, because the historical dataset may have used some corporate-action normalization, but there is no public validation-repo evidence that it did. **Approval required:** **YES**. [^DR-ALPACA][^DR-VALIDATION]

3. **Warm-up retrieval timestamp and counting method.**  
   **Verified facts:** Alpaca treats timezone-naive request times as UTC; the REST bars endpoint uses inclusive `start` and `end`; `limit` is only a maximum and the API may return fewer rows than requested; and Alpaca omits bars when no qualifying trades exist. **Validation-repo evidence:** no public page identifies a historical warm-up-counting method. **Recommended binding:** make warm-up a **calendar-anchored, explicit-UTC timestamp-window policy**, not a `limit`-driven row-count policy. In other words, the contract should count warm-up on the **retained, session-filtered 1H bars**, using explicit UTC `start`/`end` timestamps derived from the pinned market calendar, and should **not** rely on omitted start/end defaults or on `limit` to define history depth. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Medium**, because this is a pure governance binding where the historical method is not externally proven. **Approval required:** **YES**. [^DR-ALPACA][^DR-CALENDAR][^DR-VALIDATION]

4. **Market calendar.**  
   **Verified facts:** Alpaca’s calendar endpoint is authoritative for Alpaca trading days and early closes but is server-side and documented only through 2029; `pandas_market_calendars` mirrors `exchange_calendars` from v2.0 onward, ships rules as package code, and its `date_range(..., frequency='1H')` example is session-relative; `exchange_calendars` exposes `XNYS` directly and provides schedule/session methods. **Validation-repo evidence:** No explicit public calendar binding was found in the reviewed validation-repository pages. **Recommended binding:** use **`exchange_calendars` with `XNYS` as the contract calendar**, pinned to an explicit package version. **Why:** it is directly exchange-named, rich enough for sessions and interval reasoning, and more naturally pinned than Alpaca’s server-side calendar. Alpaca’s calendar should be treated as a reference cross-check, not the governing contract primitive. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Low-medium**. **Approval required:** **YES**. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

5. **Timezone conversion order.**  
   **Verified facts:** Alpaca request datetimes are UTC when naive; Alpaca returns UTC timestamps; `pandas_market_calendars` and `exchange_calendars` examples both use UTC schedules; Arrow preserves timezone-aware UTC timestamps into Arrow timestamp types. **Validation-repo evidence:** no public page states a timezone-order rule. **Recommended binding:** adopt a **UTC-first contract**: normalize bar timestamps to timezone-aware UTC immediately, build and compare the `XNYS` schedule in UTC, perform session filtering in UTC, and only then derive any America/New_York session labels or dates as secondary, display-level values. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Low-medium**. **Approval required:** **YES**. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

6. **Bar timestamp semantics.**  
   **Verified facts:** Alpaca says minute bars use the left side of the interval, and higher bars are aggregated from minute/daily bars. `pandas_market_calendars`’ 1H `date_range` example instead emits session-relative times such as `14:30`, `15:30`, and close for NYSE days. **Validation-repo evidence:** the public repo shows `1H` usage but no explicit timestamp-interpretation statement. **Recommended binding:** interpret Alpaca `1H` stock-bar timestamps as the **left edge of the provider-defined hourly bucket**—that is, a bar timestamp `t` represents the interval **[t, t + 1 hour)**. Under that binding, the regular-session-overlap hourly bars on a standard full NYSE day are the Alpaca-style clock-hour buckets, not a `09:30–10:30` session-relative convention. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Medium**, because Alpaca does not publish a separate one-hour timestamp statement as explicit as the minute-bar statement. **Approval required:** **YES**. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

7. **Missing-bar handling.**  
   **Verified facts:** Alpaca says a bar is emitted only when its fields are nonzero and qualifying underlying activity exists; if no qualifying trades occur in the interval, no bar is generated. **Validation-repo evidence:** the public validation README says no missing-bar failures were observed in that run, but it does not define any synthetic fill rule. **Recommended binding:** **do not synthesize missing hourly bars, do not forward-fill OHLCV, and do not zero-fill volume/trade count**. A missing interval remains absent in the canonical reconstruction contract. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Medium**, because some downstream pipelines prefer dense bars, but that preference is not externally evidenced here and would be less Alpaca-aligned. **Approval required:** **YES**. [^DR-ALPACA][^DR-VALIDATION]

8. **Parquet engine.**  
   **Verified facts:** pandas defaults to `engine='auto'`, which tries `pyarrow` and otherwise falls back to `fastparquet`; PyArrow exposes the richer writer control surface for Parquet. **Validation-repo evidence:** the public validation materials expose CSV artifacts, not a Parquet standard. **Recommended binding:** bind the contract to **Parquet via explicit `pyarrow`**, not pandas `auto`. Also pin the `pyarrow` package version in the governed contract record, because PyArrow releases move regularly. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Low**. **Approval required:** **YES**. [^DR-SERIALIZATION][^DR-VALIDATION]

9. **Complete dtype and serialization contract.**  
   **Verified facts:** pandas recommends explicit `StringDtype` over `object`; explicit `Int64` is the nullable integer dtype; mixed missing markers in `object` columns can vary; pandas `to_parquet` defaults include `compression='snappy'` and `index=None`; PyArrow defaults include `version='2.6'`, `use_dictionary=True`, `write_statistics=True`, `data_page_version='1.0'`, and timezone-aware UTC timestamps are preserved into Arrow timestamp fields. **Validation-repo evidence:** no public Parquet or schema contract was visible in the validation repo pages; the public evidence artifacts are CSVs. **Recommended binding:** for the canonical governed bar file, require an **explicit schema and explicit writer settings**. Specifically: timestamps as **timezone-aware UTC**; string fields as **explicit `string` or another single approved `StringDtype` choice, not `object`**; integer fields as **`int64` when nulls are forbidden and `Int64` only where nullability is expressly allowed**; price-like numerics as **`float64`**; a **fixed column order approved in the contract**; **no mixed `None`/`np.nan`/`pd.NA` object columns**; and **no `+inf`/`-inf` values permitted** as a governance policy. For Parquet writer settings, bind **`compression='snappy'`, `index=False`, `data_page_version='1.0'`, `use_deprecated_int96_timestamps=False`, and an explicit Parquet logical-type policy. The recommended binding is **`version='1.0'` with `coerce_timestamps='us'` and `allow_truncated_timestamps=False`** for the superseding contract, because the timestamps at issue are hourly and therefore do not need nanosecond storage, while Parquet 1.0 maximizes interoperability. This is a **governance preference**, not a recovered historical fact. **Byte-identical recovery support:** **NO**. **Superseding governed reconstruction support:** **YES**. **Risk:** **Medium**, because this binds a forward serialization regime rather than reproducing a historically proven one. **Approval required:** **YES**. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

## Approval boundaries

The following should be treated as **verified facts from official documentation**, not as governance preferences: Alpaca’s documented feed surfaces and defaults; Alpaca’s documented adjustment surfaces and defaults; Alpaca’s IEX-versus-SIP differences; Alpaca’s documented minute-bar left-edge rule and “no bar if no qualifying trades” rule; Alpaca’s UTC handling for request datetimes; Alpaca calendar endpoint coverage to 2029 and early-close support; pandas’ and PyArrow’s documented Parquet defaults; pandas’ documented `StringDtype` and nullable `Int64` behavior; and the public validation repo’s explicit `iex` and `1H` reliability-run evidence. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

The following are **governance preferences that still require explicit owner/governance approval** because they are not historically proven by external evidence: the choice to bind the source surface specifically to `DataFeed.IEX`; the choice to bind adjustment specifically to `RAW`; the choice to define warm-up by an explicit UTC time window rather than row count; the choice to use pinned `exchange_calendars` `XNYS` as the governing calendar; the UTC-first timezone order; the one-hour left-edge interval interpretation as the governing 1H semantic; the no-synthetic-missing-bar policy; the explicit use of `pyarrow`; and the complete dtype/serialization/writer-settings contract. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION]

Because those nine bindings are policy choices rather than recovered historical facts, **all nine should be shown as requiring explicit approval** in the next contract-resolution step, even where a recommendation is strong. [^DR-ALPACA][^DR-CALENDAR][^DR-SERIALIZATION][^DR-VALIDATION]

## Choices that still require explicit owner/governance approval

All nine recommended bindings require explicit owner/governance approval before they should be recorded as governed contract terms, because none of them is externally proven to be the exact historical configuration of the missing original dataset. The strongest evidence-supported choices are the Alpaca/IEX/1H alignment, explicit `RAW` adjustment, a pinned `XNYS` calendar, UTC-first handling, a left-edge hourly interpretation, preservation of missing intervals, explicit `pyarrow`, and a fixed explicit schema/writer contract. ## Choices that are verified facts versus governance preferences

The **verified facts** are the documented Alpaca API/SDK surfaces and defaults, the documented IEX-versus-SIP differences, the documented bar-aggregation mechanics, the documented calendar-library behaviors, the documented pandas/PyArrow serialization defaults, and the public validation repo’s explicit `iex`/`1H` reliability-run evidence. The **governance preferences** are the proposed bindings for the superseding contract: explicit IEX, explicit RAW, explicit warm-up method, explicit `XNYS`, UTC-first conversion, left-edge 1H semantics, no synthetic missing bars, explicit `pyarrow`, and the complete dtype/writer contract.
